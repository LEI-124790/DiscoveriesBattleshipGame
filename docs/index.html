Battleship

A console application for building fleets, checking ship placement, and firing at a naval battlefield. An object-oriented foundation for the game of Batalha Naval.

01 Overview

This repository contains an academic Battleship implementation by Bolinha de Canhão. Its domain model represents coordinates, ships, fleets, and a game’s firing history. Console exercises gradually introduce ship inspection, fleet management, and combat against a single fleet.

The entry point is iscteiul.ista.App. It currently calls Tasks.taskB(), so the default program manages fleets. Switch that call to Tasks.taskD() to enable firing rounds; there is no command-line mode selector.

Rules and implementation. The README describes a traditional two-player game with lettered coordinates and extra shots after a hit. The implemented exercises use integer coordinates, and task D fires three shots per round at one fleet. Player alternation is not implemented.

02 Build & run

Use a Java JDK and an installed Maven command. No Maven wrapper executable is checked in. Run the following commands from the repository root.

Build configuration needs repair first. The checked-in pom.xml is missing </dependencies> before <reporting>, so Maven cannot parse it. It also mixes maven.compiler.release=17 with source/target=25. Align the Java settings and select compatible compiler and test plugin versions before using the commands below. These are the intended workflow, not a verified successful build of the current checkout.

Compile and start the console

java -version
mvn -version
mvn compile dependency:copy-dependencies -DincludeScope=runtime
java -ea -cp "target/classes:target/dependency/*" iscteiul.ista.App

The launch command uses the macOS/Linux classpath separator. On Windows, use target/classes;target/dependency/*. The -ea flag enables the model’s Java assertions. Enter desisto to leave tasks B, C, or D.

Tests and packaging

mvn test
mvn package

The test source also needs the JUnit migration described under Tests & limitations. The intended package is target/Battleship-1.0-SNAPSHOT.jar; the POM does not configure an executable JAR or bundle runtime dependencies.

04 Ships & placement

Placement constraints

Fleet.addShip() checks capacity, board boundaries, and proximity. Ships cannot overlap or touch, including diagonally. A ship remains afloat until all of its cells have been hit.

Orientation behavior

For straight ships, both n and s extend toward increasing rows; both e and o extend toward increasing columns. A barge stores its bearing without changing its shape.

The galleon’s four orientations

The bearing selects the side with the three-cell bar. The reference coordinate is the leftmost occupied cell in the top row. East and south can occupy columns to its left on lower rows.

05 Architecture

Application startup lives in iscteiul.ista; the game model and console exercises live in iscteiul.ista.battleship. The domain is separated through four interfaces: IGame, IFleet, IShip, and IPosition.

  1. 1. ConsoleApp → Tasks
    Select an exercise, parse commands, construct fleets and games, and print feedback.
  2. 2. Game & fleetGame → IFleet
    Record shots and statistics. Find ships and validate their placement.
  3. 3. Ships & coordinatesShip → IPosition
    Build shapes, detect contact, and track damage at individual cells.
Core responsibilities and useful methods
TypeResponsibilityKey methods
GameShot history, hit/invalid/repeated/sunk counters, and board rendering.fire(), getRemainingShips(), printValidShots()
FleetShip collection, bounds and contact checks, filtering, and status.addShip(), shipAt(), getFloatingShips()
ShipAbstract shared implementation with a factory and five concrete shape subclasses.buildShip() (package-private), occupies(), tooCloseTo(), shoot()
PositionRow, column, and mutable hit/occupancy flags. Equality compares coordinates.equals(), isAdjacentTo(), shoot()
CompassCardinal bearings and an UNKNOWN value for unrecognized input.charToCompass() (package-private), getDirection()

What happens when a shot is fired?

  1. Game.fire(position) validates the coordinates. A rejected shot increments the invalid counter.
  2. A previously recorded coordinate increments the repeated counter and causes no further damage.
  3. A new valid position enters the shot history. The fleet looks for a ship at those coordinates.
  4. If a ship is present, its matching cell is marked hit and the hit counter increases.
  5. If no unhit cells remain, the sunk counter increases and fire() returns that ship. All other outcomes return null.

Use the counters to distinguish a miss from a hit that does not sink a ship. Board validity currently has an upper-bound defect described below.

07 Git commands & workflow

The repository history shows contributors working on branches such as LEI-124790-Javadoc, pedro-javadoc, and alfena, bringing changes from main into their branches, and integrating work through pull-request merge commits.

Reading the history. These commands describe a possible workflow consistent with the project’s commit graph. Git records commits and their parents, not the exact terminal commands or IDE actions used to create them. The examples below are instructions; they have not been executed to change this repository.

1. Clone and inspect the project

For a new checkout, clone the repository and enter its directory. Skip this step if you already have the project locally.

git clone https://github.com/LEI-124790/DiscoveriesBattleshipGame.git
cd DiscoveriesBattleshipGame

The inspected checkout is named ES1. Its origin uses git@github-school:LEI-124790/DiscoveriesBattleshipGame.git, which depends on a locally configured SSH host alias named github-school. The HTTPS example avoids that machine-specific alias.

2. Start a branch for new work

With a clean working tree, update local main and create a branch for this documentation. docs/project-guide is an example new branch name.

git switch main
git pull --ff-only origin main
git switch -c docs/project-guide

--ff-only updates the branch only when no merge commit is needed; it stops if the histories have diverged. To resume an existing local branch instead, use git switch LEI-124790-Javadoc. If that branch exists only on the remote, first fetch and then use git switch --track origin/LEI-124790-Javadoc.

3. Stage, commit, and push

After editing the documentation on your branch, stage that file, review the staged content, and create a commit. Use the relevant source-file paths instead when working on Java changes.

git status
git add docs/index.html
git diff --cached
git commit -m "docs: add project documentation and Git workflow"
git push -u origin docs/project-guide

git add prepares content for a commit; git commit records it locally; git push publishes the branch’s commits. The first push’s -u establishes the upstream so later pushes from that branch can use git push.

4. Bring main into a working branch

To incorporate teammates’ merged changes while keeping your branch active, fetch the remote history and merge origin/main. Commit or stash unfinished changes before merging.

git switch docs/project-guide
git fetch origin
git merge origin/main

git fetch updates remote-tracking references without changing your working files. The merge combines the fetched main history with your branch. A merge commit is created when the histories have diverged; otherwise Git may fast-forward or report that the branch is already up to date.

If conflicts occur, list them, edit each affected file to resolve the competing changes, and stage the resolutions. For example, if Tasks.java is the conflicted file:

git status
git diff --name-only --diff-filter=U
# Edit the conflicted files and remove conflict markers.
git add src/main/java/iscteiul/ista/battleship/Tasks.java
# Stage any other resolved files, then finish the merge.
git merge --continue

Use git merge --abort to cancel an in-progress merge instead. Once the merge completes and you have reviewed the result, publish the updated branch with git push.

5. Open and merge a pull request

On GitHub, open a pull request with base: main and compare: docs/project-guide. Review the changes and merge using Create a merge commit to preserve a graph like the project’s existing history. Pushing a branch alone does not open or merge a pull request.

If the GitHub CLI is installed and authenticated, the equivalent creation step is:

gh pr create --base main --head docs/project-guide \
  --title "Add project documentation" \
  --body "Document setup, gameplay, architecture, and the Git workflow."
gh pr view --web

gh is a separate GitHub tool, not a Git subcommand. Review and merge the pull request on GitHub, then synchronize your local main branch:

git switch main
git pull --ff-only origin main
git branch -d docs/project-guide

The final command is optional cleanup: it deletes the merged local branch. It does not delete the branch on GitHub.

08 Tests & limitations

The only checked-in test, AppTest, extends the legacy junit.framework.TestCase and asserts true. It does not exercise game behavior. The declared Jupiter dependency does not match those imports. The checked-in GitHub workflow synchronizes labels; it does not build or test the application.

  • Build and test configurationThe POM’s missing closing tag prevents XML parsing. Its Java version settings disagree, and the legacy test needs migration to Jupiter or an appropriate legacy dependency. See Build & run before attempting a build.
  • Fleet threshold and compositionIFleet.FLEET_SIZE is 10, but both Fleet.addShip() and Tasks.buildFleet() use <= checks. The result is 11 accepted ships. This matches the README’s total by coincidence; category quotas are not enforced.
  • Shot boundary validationGame.validShot() accepts a row or column equal to 10. Rendering uses a 10 × 10 array with indices 0–9, so recording such a shot and then running ver can throw an array index exception.
  • Input handling and game completionMalformed numbers, invalid ship bearings, or exhausted input can terminate an exercise with an exception. B–D expect desisto to exit. In D, sinking the final ship logs a message but does not leave the command loop.
  • Task C map outputTask C logs the fleet object, and Fleet has no custom toString(). Use task D’s mapa for a rendered board.
  • Mutable collections and position hashinggetShips(), getPositions(), and getShots() expose their underlying mutable lists. External mutations can bypass validation. Position.equals() compares coordinates, while hashCode() also includes mutable flags, which can make hash-based collections behave incorrectly.

Useful next verification work

After repairing the build, add behavioral coverage for ship geometry, diagonal separation, fleet capacity, coordinates at the board edges, repeated shots, sinking, and input errors. Resolve the intended fleet size and turn rules before treating the current exercise behavior as a complete game specification.
